# 项目审查与闭环清单

审查日期：2026-11-06（Europe/Rome）。对象：当前目录中的 v1.4.0 源码。

## 结论

项目已经具备清晰的 Telegram Bot 基础架构和若干可靠性设计，但当前源码没有通过完整质量门禁，不应直接认定为可生产交付版本。优先工作是修复构建、错误日志、数据删除与 Worker 故障路径，再完成真实环境验收。

项目现有业务是反馈收集，没有定义客服、支付或其他业务产品。是否增加反馈回复、工单状态等功能，应由实际用途决定；下面把实现缺陷和产品扩展分开。

## 上线前应完成的修复

### 1. P1：补齐真实锁文件与可重复构建

证据：根目录没有 `pnpm-lock.yaml`；`Dockerfile:7`、`scripts/gcp/deploy.sh:5`、`.github/workflows/ci.yml:34` 均明确拒绝缺少锁文件的构建。

影响：当前交付内容无法直接通过既定 CI、Docker 或生产部署。只修复代码而不锁定依赖，也无法稳定复现本次检查结果。

闭环标准：用项目指定 pnpm 10.21.0 生成真实锁文件，纳入版本管理；干净环境 frozen install、Prisma generate、所有质量门禁及 Docker 构建通过。不能用临时 npm 锁文件替代。

### 2. P1：修复生产编译和类型检查

证据：

- `src/queue/notifications.ts:2`、`src/security/rate-limit.ts:1`、`src/worker.ts:7` 及两个诊断脚本默认导入 ioredis；当前 NodeNext 类型解析下产生不可构造/不能作类型使用的错误。
- `src/server.ts:77` 在 Fastify 错误处理器内直接读取 unknown 的 `statusCode`，产生 3 处类型错误。
- `scripts/doctor.ts:59`、`scripts/webhook-status.ts:10` 对类型上可选的 `url` 直接取 `.length`。
- `tests/telegram-text.test.ts:22` 使用不存在的 `toEndWith`。

闭环标准：按实际锁定依赖修正导入及错误类型收窄，正确处理可选 URL；全项目 typecheck 和生产 build 均以退出码 0 结束。生产编译本身有 7 处错误，所以不能仅排除测试文件来解决。

### 3. P1：恢复有效的测试和 lint 门禁

证据：Unicode 测试的 `expect(msg).toEndWith('…')` 在 Vitest 中报 `Invalid Chai property`；`scripts/offline-smoke.mjs:101`、`:106` 的 Buffer/console 未声明 Node globals；`tests/privacy-export.test.ts:47` 的 `_args` 被现有规则判为未使用。

闭环标准：改用受支持的断言，如 `expect(msg.endsWith('…')).toBe(true)`；给 JS 脚本配置适当运行环境，清理无用参数。先跑通现有测试，再补下面列出的真实风险回归；不要通过跳过测试或关掉全部规则得到绿灯。

### 4. P1：异常日志会泄露反馈正文和身份

证据：`src/observability/logger.ts:8` 只脱敏少数 Header 和顶层 token。`src/bot/create-bot.ts:82`、`:349`、`src/worker.ts:88` 附近直接记录原异常。实际构造一次 sendMessage 的 GrammyError 后，Pino 输出了 `err.payload.text` 和 `err.payload.chat_id`。

影响：管理员通知发送失败时，完整通知正文（含反馈）会进入日志；这违反了代码注释所述“不记录正文”的边界。Sentry 也直接接收原异常，需要单独确认其采集和脱敏行为，本次没有实发 Sentry。

闭环标准：对日志错误采用字段白名单/专用 serializer，移除 payload、request、上下文等敏感内容；Sentry 增加对应过滤。用带明显合成标记的反馈和导出失败验证日志及遥测中均无正文、身份和凭据。grammY 的 [GrammyError 文档](https://grammy.dev/ref/core/grammyerror) 明确公开了 payload 属性。

### 5. P1：删除数据被 Telegram 按钮应答失败阻断

证据：`src/bot/create-bot.ts:245` 先 `await ctx.answerCallbackQuery()`，下一行才 `deleteMyData`。在 API 替身返回“query is too old / invalid”时，处理器直接抛错，数据库删除调用次数为 0。

影响：数据库正常、签名仍有效时，回调应答失败也会导致删除请求没有执行；旧 callback 被重复投递时可能持续失败。

闭环标准：将按钮应答作为尽力完成的 UI 操作，确保已授权的数据库删除不会依赖它；数据库删除失败仍需明确失败和重试语义。补过期 query、应答网络失败、数据库失败和重放回归。

### 6. P1：Worker 的 Redis 故障会阻塞启动后续流程及关停

证据：`src/worker.ts:34` 的 Redis 连接使用 `maxRetriesPerRequest: null`，补偿 Queue 复用该连接；`:161` 在注册留存清理、积压检查和 SIGTERM 处理器前等待首次扫描。只要存在待补偿记录，扫描就会在 `getJob` 等命令上等待 Redis。正常关停时 `:245` 又先等待 activeSweep，最后才断开 Redis。

影响（代码路径与连接语义推导，未做真实 Redis 故障注入）：Redis 长期不可用且存在待通知数据时，启动可能无法进入留存清理/积压告警阶段；运行中挂起的扫描也可能让关停一直等待，最终被平台强制终止。

闭环标准：在任何可阻塞启动步骤前注册退出处理；补偿生产者使用有界等待的独立连接；数据库维护和健康检查不等待 Redis；关停有总时限及取消路径。验证 Redis 启动即不可用、运行中断网和 SIGTERM 场景。BullMQ 的 [连接文档](https://docs.bullmq.io/guide/connections) 区分了消费者持续重连与生产者及时失败的需求。

### 7. P1：生产发布未绑定同一版本的质量结果

证据：`.github/workflows/cd-gcp.yml:44` 起只有 checkout、锁文件存在检查、认证与部署；没有执行测试，也没有验证目标提交的 CI 成功状态。审批是人工配置条件，不能替代自动质量验证。部署脚本先切换 HTTP 服务，再部署 Worker，后一步失败不会自动恢复前一步。

闭环标准：只发布已通过质量门禁的提交/镜像；构建一次并以 digest 推送到 staging/production；发布后自动验证 ready、Worker 与测试反馈；记录提交、镜像摘要、Secret 版本、上一个兼容版本。首次 Webhook 注册可以保留显式操作，但必须作为验收项检查实际 URL 和密钥一致性。

## 需要补齐的可靠性和隐私流程

### 8. P2：有状态命令的更新重放保护不完整

证据：只有 Feedback 记录通过 `sourceUpdateId` 去重，`/feedback` 与 `/cancel` 没有更新回执。用真实 bot.handleUpdate + 替身数据库执行 `/feedback(1) → /cancel(2) → 重放 /feedback(1)` 后，已取消状态重新变为 awaitingFeedback=true。

影响：较旧更新重试或乱序时可能重新激活流程，后续普通文本被当成反馈。降低 webhook max_connections 只能减小并发，不消除重试。

闭环标准：为会改变会话状态的命令增加持久更新回执或等价的版本控制，按用户处理状态竞争。测试重复命令、乱序、保存后回复失败和并发取消。不要仅对反馈 INSERT 去重后就宣称整个业务幂等。

### 9. P2：删除确认码可复用、取消不能撤销签名

证据：`src/privacy/delete-confirm.ts:28` 仅验证用户、签名和时间，没有 nonce 的消费状态；相同码连续校验均为 true。取消按钮只清除当前消息键盘，不撤销已签发的确认码。私聊中每次 update 又会先 touchUser。

影响：有效期内已用或已取消的确认码仍能接受重放；如果用户记录/反馈随后重建，旧请求可以再次删除新数据。用户绑定正确，没有发现拿自己的确认码删除他人记录的路径。

闭环标准：按实际交互要求采用可消费、可取消的 nonce，或账户删除版本；已使用/已取消按钮不能作用于新数据。覆盖“删除后重新提交反馈，再重放旧确认”的测试。

### 10. P2：保留策略与通知配置耦合

证据：Worker 必须同时有 Redis 和管理员 ID 才能启动，而唯一清理入口也在这个 Worker。Bot 配置允许单独启用 FEEDBACK_RETENTION_DAYS，隐私文案随即显示保留期限，即使维护进程没有部署。每分钟最多清理 500 条，积压时不会严格在到期瞬间删除。

闭环标准：让维护任务能独立于管理员通知运行，或拒绝无法执行的组合配置；监测最后成功清理时间、最老过期记录年龄、删除数量和失败次数。面对大量历史数据要有排空策略；对外表述实际能兑现的时限。

### 11. P2：GCP 重部署可能清掉监控配置

证据：`scripts/gcp/deploy.sh:48`、`:60` 只列出四个秘密和固定环境变量，遗漏 SENTRY_DSN、METRICS_TOKEN；部署又使用 `--set-env-vars` 和 `--set-secrets`。

影响：按脚本部署时无法启用这两个功能；如果此前在云控制台手动补上，下一次脚本部署可能删除它们。该结论来自脚本与 [gcloud 参数的覆盖语义](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)，未在真实账号执行。

闭环标准：将所有受支持配置纳入部署声明和 CI Variables/Secret 引用；明确全量声明还是增量更新；连续部署两次验证监控配置持续存在。不能只在本地 `.env.example` 声明功能。

### 12. P2：通知失败有自动重试，但缺少人工结案能力

现状：数据库作为通知事实来源、稳定 Job ID、租约、补偿扫描都已具备。永久 403、管理员未启动 Bot、错误管理员 ID 等仍会进入周期重试；缺少按反馈 ID 查看最近失败、暂停、重新投递或确认无需发送的受控操作。

闭环标准：区分暂时故障和需要人工修正的错误；可查询最后错误类别/时间/累计次数；有可审计的重试、暂停、终止路径。避免无限重复告警而没有处理入口。无须为普通反馈实现跨 Telegram 与数据库的 exactly-once。

### 13. P2：监控没有覆盖“Worker 完全停止”

现状：HTTP readiness 只验证数据库；`/status` 的 queue online 只是 Redis 可达；积压检查运行在 Worker 自身，Worker 停止时它也停止。Prometheus 主要是更新处理和 Node 指标，没有 Worker 心跳、清理延迟或通知成功率。

闭环标准：外部独立检查 Worker 心跳、待投递数量和最老年龄、失败率、留存任务活跃时间；配置可实际送达值班人的告警并做触发演练。区分“Redis 正常”和“有消费者工作”。

### 14. P2：故障、并发与端到端测试证据不足

现状：测试主要覆盖纯函数、查询参数和 HTTP 拒绝路径；数据库集成只有 2 个测试，租约的领取是顺序调用，并未证明两个真实进程并发的行为。没有真实 Redis、Worker 通知发送、Bot 完整流程或部署启动测试。

闭环标准：先为本次已复现的 3 个关键缺陷补回归；再执行真实 PostgreSQL 并发消费/租约/级联删除、Redis 中断恢复、Telegram 429/5xx、重启和超时、导出多页隔离、staging 全流程。指定隔离数据库，保存日志与运行结果。

### 15. P2：用户可见隐私说明没有解释所有副本边界

证据：`src/domain/i18n.ts:20`、`:57` 提供导出和删除说明，但没有向终端用户说明已发送给管理员的消息、Telegram 导出文件、备份和日志副本的保留/删除边界。这些限制主要写在开发运维文档里。

闭环标准：把适用的范围说明放到用户可访问的隐私说明或链接中，并确定运营联系人、实际数据保留安排、备份恢复后的删除请求处理策略。已有在途通知可能与删除并发，也需明确边界；本审查不替代法律意见。

## 较低优先级与维护事项

- 开发依赖安全：本次 npm audit 报告的 7 个 moderate 命中源自 minimatch 的 [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249)。按实际锁文件升级或评估兼容的覆盖方案；不要将开发工具链公告写成公网 Bot 已有 7 个漏洞。生产依赖本次未命中公告也不证明不存在应用漏洞。
- 文档漂移：`docs/OPERATIONS.md` 开头仍声称 `/ready` 会 ping Redis，但代码和后续文档明确不检查；`.env.example` 关于单连接“保序”的表述也强于实际保证。更新历史 VALIDATION 时应保留日期和证据，不把历史结果覆盖成当前全部通过。
- 格式和门禁：已有 Prettier 配置但原文件大量不符合，且 CI 不跑 format:check。统一格式后再启用检查，不应与故障修复混成难审阅的大改动。
- 可维护性：`create-bot.ts` 和 `worker.ts` 同时承担命令、鉴权、隐私、调度、关停等多种职责。先修复行为，再抽取可独立测试的处理器和调度组件，不必重写框架。
- 源码与发布追踪：当前是没有 Git 元数据的源码包。确认实际维护仓库、提交锁文件、分支保护和发布负责人；基础镜像及 Actions 可考虑固定 digest/SHA 并通过自动升级维护。UTC 秒级镜像 tag 不是强制不可变镜像策略。
- 通知容量：补偿每分钟最多扫描 200 条；大规模 Redis 数据丢失时恢复吞吐有限。先测量目标流量与恢复目标，再调整批量、间隔和告警阈值。
- 运维演练：备份/PITR、恢复、Token 轮换、管理员无法接收消息、Worker Pool 不可用和回滚均只有要求或说明，没有本次实际执行证据。需要明确恢复目标与负责人。
- 成本和环境：Cloud SQL、Redis、常驻 Worker 都可能持续计费。是否保留 GCP 全套基础设施应由流量、可用性和预算决定；没有必要在尚未完成构建验收前增加更多平台。

## 业务闭环如何判断

| 流程         | 当前实现                             | 尚未闭环的部分                                                                                  |
| ------------ | ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 用户设置     | 语言菜单 + 数据库存储                | 真实键盘回调、重启后读取的端到端证据                                                            |
| 反馈采集     | 进入输入 → 校验 → 原子保存 → 确认    | 命令重放、非文本输入引导、限流后用户是否知道请求被忽略                                          |
| 管理员通知   | 保存 → 入队 → 领取租约 → 发送 → 标记 | 永久失败的人工处置、独立告警、真实中断恢复验收                                                  |
| 数据导出     | 私聊身份过滤 + 50 条分页 + JSON      | 多页真实数据库验证；如果业务要求同一时间点完整快照，需要额外设计                                |
| 数据删除     | 签名按钮 → 级联删除 → 回复           | 回调应答失败、旧签名复用、备份/通知副本说明                                                     |
| 保留清理     | 可选批量删除                         | 无通知配置时的独立运行、延期检测与告警                                                          |
| 软件发布     | 手动审批、迁移优先、脚本部署         | 锁文件、质量通过证据、同一镜像晋级、发布后验证和完整回滚                                        |
| 用户反馈处理 | 管理员能查看最近 5 条                | 若定位为客服/运营工具，还需要受理、负责人、回复、结案和查询；若仅作意见箱，可明确告知不保证回复 |

现阶段不建议直接增加支付、多租户、复杂后台或迁移框架。应先定义目标用户、核心用途、反馈是否承诺回复和上线规模，再决定是否需要业务扩展。

## 建议执行顺序与完成标准

1. **建立可验证基线**：确定维护仓库和锁文件；修复 12 处类型诊断、3 个 lint 错误和无效测试断言；干净安装后全部门禁通过。
2. **修复真实行为缺陷**：错误日志白名单、删除应答解耦、有状态命令重放保护、确认码撤销/一次性语义、Worker 有界启动与关停；对应回归通过。
3. **把运营路径接起来**：独立保留清理、监控配置可重复部署、Worker 外部心跳、永久通知故障人工处理入口；实际触发一次报警并完成处理。
4. **完成 staging 验收**：隔离 PostgreSQL/Redis、Docker 两种进程启动、真实 Telegram 命令和菜单、导出/删除、断网恢复、并发、429/5xx、发布/回滚；保存结果。
5. **按产品目标补业务闭环**：决定意见箱或客服流程，补用户说明与必要的受理/回复/结案能力；明确运营负责人、成本和恢复目标后发布。

完成的判断依据应是可重复的检查结果、真实环境验证和有人负责的故障处理路径，而不是文档中写有“生产级”或验收清单文件已经存在。
